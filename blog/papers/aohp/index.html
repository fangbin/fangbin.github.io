AOHP: 把操作系统重新设计为智能体的原生运行环境

AOHP: An Open-Source OS-Level Agent Harness for Personalized, Efficient and Secure Interaction

清华/北大/港大联合团队在 AOSP 上构建了一个智能体原生操作系统——AOHP（Android Open Harness Project），将 AI Agent 提升为 OS 一级主体，通过个性化服务组合、高效智能体接口和安全信息流三大机制，实现了任务完成率 +21.12%、Token 消耗 -51.55% 的显著提升。

Shanhui Zhao (Tsinghua), Jiacheng Liu (Peking), Guohong Liu (Tsinghua), Jichao Yan (Tsinghua), Jialei Ye (Peking), Yuhao Yang (HKU), Yunxin Liu (Tsinghua, corr.), Yuanchun Li (Tsinghua, corr.)

1. 论文概览

当前的 AI Agent 已经能够自主调用工具、跨应用检索信息、管理内存并完成多步骤任务。但一个根本性的架构矛盾正在浮现：现代 Agent 的工作模式与传统操作系统以应用为中心的架构设计之间存在系统性不匹配。

传统操作系统（包括 Android）的基本假设是——用户直接操作开发者定义的 GUI，一次只运行一个前台应用，权限管理绑定在应用边界上。这些假设在面对 Agent 工作流时全面失效：Agent 需要跨应用传递数据、并行执行后台任务、处理事件流、在上下文中保留长期记忆，而这一切在现有 OS 的抽象层上没有原语支持。

AOHP（Android Open Harness Project）试图从根本上解决这个问题。它不是构建一个新的 Agent 框架，而是直接在 AOSP（Android Open Source Project）源码层面进行修改，将 Agent 提升为操作系统的一级主体。这意味着：系统资源调度、UI 渲染、文件系统、权限模型——所有这些 OS 核心机制都围绕 Agent 的需求重新设计。

AOHP 在保留完整 Android 兼容性的前提下，引入了三大 OS 级机制：(1) 个性化服务组合——根据用户意图动态合成跨应用的交互界面；(2) 高效智能体接口——为 Agent 提供并行后台执行、结构化 UI、事件流订阅等原生抽象；(3) 安全信息流——通过污点追踪和敏感值沙箱实现细粒度的数据保护。在 30 项真实移动端任务的基准测试中，AOHP 将任务完成率从 54.44% 提升至 75.56%，Token 消耗降低 51.55%。

图 1: AOHP 的四层垂直架构——底层兼容 Android 生态，向上依次提供统一交互接口、能力编排层和个性化服务组合，同时以两大跨层机制（高效智能体接口 + 安全信息流）贯穿全栈。

2. 核心创新

2.1 智能体作为操作系统一级主体

这是 AOHP 最根本的设计决策。在传统 Android 中，Agent 只是一个"外部调用者"——它通过无障碍服务（Accessibility Service）观察屏幕像素、通过 shell 命令执行操作，本质上是在模拟一个人类用户。这种架构带来的代价是巨大的：每次操作都需要截屏 → 解析 → 定位 → 点击/滑动 → 等待结果，中间每一步都伴随着过度渲染、序列化瓶颈和脆弱的 GUI 定位。

AOHP 将 Agent 提升为与人类用户平等的 OS 一级主体（first-class OS actor）。具体而言：

  • Agent 拥有独立的执行上下文，不与物理屏幕耦合，可以在虚拟显示中并行运行
  • Agent 可以直接访问结构化 UI 表示（而非像素），避免视觉解析步骤
  • Agent 通过 Event Stream 订阅系统事件（通知、传感器），而非轮询
  • 文件系统向 Agent 暴露统一文件快捷方式（Unified File Shortcut），使 GUI 操作文件的结果可直接反射为结构化文件观测

2.2 生成式服务入口——"用户自定义应用"

AOHP 最直观的用户体验变革是 User-Defined Apps。传统应用中，交互界面由开发者一次定义、永久固定。AOHP 的个性化服务组合层（Personalized Service Composition）将应用重新定义为由 OS Agent 动态合成的服务入口。

每个生成式入口包含三个组件：

  • Task Schema：定义用户意图（如"比较预算内的鞋子"、"补货家居用品"）
  • Service Graph：将意图映射到跨 API/CLI/GUI 的具体服务能力
  • Presentation Policy：决定哪些中间结果呈现给用户，哪些保留在 Agent 内部

论文中展示了三个具体 Demo：Health Hub（聚合多应用健身/睡眠/体重数据）、Gift Picker（为纪念日生成奢侈品推荐应用）、Python Learning Assistant（儿童编程辅导应用）。其运行是真实的——视频 Demo 可在项目主页查看。

2.3 安全信息流——"敏感数据不应进入 Agent 上下文"

AOHP 的安全设计建立在一个前提之上：Agent 的上下文是攻击面和隐私泄露面的核心。一旦敏感明文（银行卡号、家庭住址、转账金额）进入了 Agent 的 LLM 上下文，它就变得不可控——可能被模型记忆、被其他工具调用意外泄露、或被 prompt injection 诱导输出。

AOHP 的解决方案是让敏感数据完全绕过 Agent 上下文：

  1. Source Sanitization：在敏感数据流向 Agent 时，系统自动将明文替换为类型化占位符（如 <payment-card:uuid>）
  2. Trusted Vault Executor：当 Agent 需要对敏感数据执行操作时，它提交意图（而非数据本身）给可信执行器，由后者在受信环境中完成操作
  3. Taint Tracking：从数据进入系统开始，污点元数据跟随数据流经复制、变换、组合、传输的全链路
  4. Policy Enforcement：在系统出口和状态变更边界检查污点标记，决定是否需要用户显式审批

安全评测中，AOHP 在全部 5 类测试用例（敏感显示脱敏、普通操作免审批、敏感操作需确认、未授权默认拒绝、事件脱敏追溯）均通过。

3. 系统架构与方法论

3.1 四层垂直架构

AOHP 的架构从下到上组织为四层：

L1 — Android 生态层（兼容层）：保留完整的 Android 应用、系统服务、硬件驱动和平台 API。AOHP 不做"从零开始的 OS"，而是在成熟生态上叠加 Agent 原语。

L2 — 统一交互接口层：将传统 Android 接口和新兴 Agent 接口归一化为四种调用模式：API、CLI、Structured UI 和 Rendered GUI。这个设计的巧妙之处在于：Agent 优先选择符号化路径（API/CLI/Structured UI），仅在兼容性需要时回退到 GUI 视觉操作。

L3 — AOHP 能力层：提供三个 OS 级能力模块——System Memory（跨应用的偏好存储和任务状态）、Skills（可复用的服务能力封装）、UI Utilities（生成式入口的 UI 构建工具）。

L4 — 个性化服务组合层：将 L3 的能力组装为面向用户的服务入口。用户看到的是"购物""健康"等任务级概念，而非"A 应用的第 3 个 Tab"。

3.2 高效智能体接口（五大原语）

这一机制直击 Agent 在移动端执行的核心效率瓶颈：

  • 并行后台交互：轻量级虚拟显示（Lightweight Virtual Displays）使 Agent 可以在后台并行运行多个工作流，不再受物理屏幕的单一前台限制。
  • Agent-aware UI 增强：将传统 GUI 抽象为低冗余、高语义的结构化表示，同时保留渲染 GUI 作为回退。
  • 原生沙箱运行时：提供一个 OS 管理的独立执行环境，Agent 可在其中执行代码、处理数据、运行长期服务，中间结果不进入 Agent 上下文。
  • 统一文件快捷方式：将文件提升为 OS 边界的一等对象——GUI 操作文件的结果自动反射为结构化观测，Agent 也可以通过统一的系统接口将文件交给另一个应用。
  • 事件流抽象：支持通知捕获缓冲和传感器流订阅，Agent 从"轮询模式"转变为"事件驱动模式"。

3.3 个性化服务组合流程

组合流程可以概括为：

意图解析 → 能力发现 → 服务编排 → 入口生成 → 个性化注入

具体而言，OS Agent 首先解析用户的自然语言意图；然后扫描 API/CLI/GUI 通道中的可用服务能力（每个能力包含 I/O schema、前置条件、副作用和策略标签）；接着将这些能力组合为高阶工作流（面向约束——例如搜索可以并行、购买必须显式确认）；最后注入 System Memory 中的持久偏好和任务上下文，生成最终的个性化服务入口。

4. 实验结果

4.1 基准设计

AOHP 评估使用 OpenClaw Agent 作为统一的上层 Agent 框架，在 AOHP 和原生 Android 两个环境中运行相同的 30 项真实移动端任务。任务覆盖 6 个能力类别：GUI 操作、非 GUI 操作、事件捕获、多源信息检索、记忆管理和混合工作流。

4.3 提升来源分析

AOHP 的优势集中于三类任务：

  • 瞬态通知任务：Event Stream 让 Agent 不再丢失 Toast/弹出通知
  • 细粒度 GUI 操作：Structured UI 避免了层层视图树导航
  • 跨应用/记忆依赖工作流：Unified File Shortcut、System Memory 和 Background Execution 分别从数据层、状态层和执行层减少了中间步骤

Token 消耗降低的核心原因是"更少的步骤 → 更短的上下文"——Agent 每一步的操作和观测都会堆积到上下文中，AOHP 用更少的步骤完成相同任务，上下文自然更紧凑。具体而言，输入 Token 减少 51.50%，输出 Token 减少 57.48%。

4.4 安全评测

基于标注支付应用的 5 项安全测试全部通过。值得强调的是"未授权默认拒绝"（Fail-Closed）的设计——当访问请求超出声明的策略范围时，系统默认拒绝而非暴露敏感数据。这与传统 Android 的"默认允许 + 运行时权限弹窗"模型形成鲜明对比。

5. 启示与思考

5.1 这不是"又一个 Agent 框架"

AOHP 与之前我们解读过的 AgentSpec、RAVEN/PropagandaAI、Intent-to-Execution Integrity 等安全论文有着本质不同的定位。那些工作在Agent 层或LLM 层进行约束和检测；AOHP 工作在OS 内核与框架层——它在 Agent 还没有产生不安全行为之前，就已经改变了系统暴露给 Agent 的抽象接口。

打个比方：如果 AgentSpec 是在桥头设卡检查每一辆过桥的车，那么 AOHP 是重新设计了桥的结构——把狭窄的吊桥改成了双向八车道高速，同时在路面上直接铺设了感应线圈。两者的安全哲学是一致的（确定性执行、策略外置化），但操作的层级不同。

5.2 Agent-Native OS 的范式意义

这个工作让我想到一个更宏大的趋势：Agent 正在从"浏览器内的聊天机器人"逐步下沉，成为操作系统、硬件、物联网的通用交互层。Apple Intelligence、Microsoft Copilot、Google Gemini 都在朝这个方向走，但 AOHP 的独特贡献在于它把这条路走通了——在一个真实的、开源的移动操作系统中展示了完整的技术可行性，并且开源了全部代码。

三个设计原则值得未来的 Agent-Native 系统借鉴：

  1. 接口中立：不要让 Agent 必须依赖 GUI 像素（这太贵了），也不要让 Agent 必须调用私有 API（这太脆弱了）。提供多层次的、可回退的接口。
  2. 敏感数据不应进入 Agent 上下文：AOHP 的安全信息流模型——Source Sanitization → Vault → Taint Tracking——应该成为 Agent OS 安全的标准范式。
  3. 系统记忆是 OS 的职责，不是 Agent 的职责：跨应用的个人偏好和任务状态应该由 OS 管理，而不是让每个 Agent 自己维护一个向量数据库。

5.3 局限性与开放问题

论文坦诚地列出了四个未来工作方向：

  • 兼容性覆盖：对自定义渲染、反自动化逻辑、未文档化行为的应用支持需要加强
  • 能力发现自动化：目前依赖开发者标注和手动描述，需要自动推理遗留应用的服务能力
  • 资源调度：虚拟显示、沙箱运行时、事件流的并发执行需要移动端的热/内存限制策略
  • 策略可用性：细粒度信息流控制产生了大量审批决策，用户界面需要更智能的分组和解释

从更广的视角看，AOHP 目前仍是一个研究原型。它证明了"Agent-Native OS"在技术上是可行的、性能上是优越的、安全上是可验证的。但从原型到面向消费者的产品，中间还有驱动兼容性、应用商店生态、安全审计、用户教育等大量工程化问题要解决——这些正是开源项目可以逐步积累的。
